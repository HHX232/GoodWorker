# Спецификация: Шахматы в GoodWorker

## Задача

Репетитор шахмат и его ученики сейчас не могут заниматься шахматами на платформе: есть только
игрушечная партия против слабого самописного бота. Нельзя выбрать «шахматы» предметом урока,
нельзя показать доску в звонке, нельзя собрать курс с позициями и задачами, нет базы задач.
Ученик, играющий сам, не понимает, почему его ход плохой: движок показывает цифру, а не смысл.

## Решение

Раздел «Шахматы» (`/chess`): игра против сильного движка с уровнями, решебник задач из открытой
базы Lichess, список тактик и дебютов для изучения — и везде бесплатный ИИ-тренер, который
объясняет ход человеческим языком. Несколько скинов фигур и доски. Предмет «Шахматы» на платформе:
его можно выбрать для звонка (тогда в звонке появляется общая доска) и для курса (в конструкторе
появляются шахматные блоки). Три прототипа Hero для будущего лендинга.

## Решения по реализации

1. **Движок — Stockfish из npm `stockfish` (GPL-3), сборка lite single-thread WASM**, копируется в `public/stockfish/` (не в бандл). Почему: самый сильный открытый движок; single-thread не требует COOP/COEP-заголовков, которые сломали бы встраиваемые ресурсы сайта. Работает в Web Worker в браузере — сервер не платит за расчёт, поэтому оценка бесплатна и безлимитна. Пакет весит ~200 МБ распакованным — в репо попадает только нужный файл (~7 МБ), пакет в `devDependencies` + скрипт копирования.
2. **Уровни 1–8** — таблица в одном месте: `Skill Level` (0…20), `movetime`, для 1–3 ещё `UCI_LimitStrength`+`UCI_Elo` (1320/1500/1700). Уровень 8 = Skill 20, 2 с.
3. **Тренер = движок (факты) + DeepSeek (слова).** Клиент считает MultiPV 3 до хода и оценку после; классифицирует ход по потере оценки (в сантипешках, с учётом мата): лучший (=топ-1) / хороший (≤ 50) / неточность (≤ 100) / ошибка (≤ 300) / зевок (> 300). Сервер `POST /api/chess/coach` перепроверяет FEN и легальность хода через `chess.js`, добавляет вычислимые факты (что бьётся, что висит после хода, шах/мат, изменение материала) и вызывает существующий `callAI` (DeepSeek). Промпт: «2–4 предложения, без новых вариантов кроме переданных, ходы — в SAN, язык = locale». Почему так: LLM плохо считает шахматы, поэтому ей запрещено считать — она только переводит факты движка в речь.
4. **Лимиты объяснений** через существующий `checkRateLimit` (таблица `RateLimit`): ключ `chess-coach:ip:<ip>` (гость, 5/24ч) или `chess-coach:user:<id>` (100/24ч), VIP (`isVip && vipExpiresAt > now` у Student или Teacher) — без проверки. Числа — константы в одном файле (ASSUMPTION, пользователь дал «маленький / большой / без лимита»). Сбой DeepSeek не списывает попытку (вызов `checkRateLimit` только после успешного ответа модели — допустимое перерасходование одной гонки).
5. **База задач — Lichess puzzle DB (CC0)**, `database.lichess.org/lichess_db_puzzle.csv.zst`. Скрипт импорта качает, распаковывает потоком (`zstd` CLI), отбирает ≈50 000: `Popularity ≥ 80`, `NbPlays ≥ 300`, равномерно по корзинам рейтинга 400–2800 (шаг 200) и с гарантией ≥ 500 задач на каждую тему из списка тактик. Пишет в таблицу батчами `createMany skipDuplicates`. Идемпотентен. Почему подмножество: 5,6 млн строк — 1 ГБ в общей БД ради задач, до которых никто не дойдёт.
6. **Данные (Prisma):**
   ```prisma
   model ChessPuzzle {
     id         String   @id            // lichess PuzzleId
     fen        String
     moves      String                  // UCI через пробел; moves[0] — ход соперника
     rating     Int
     themes     String[]
     openingTags String[]
     popularity Int
     @@index([rating])
   }
   model ChessPuzzleAttempt {
     id        String   @id @default(cuid())
     userId    String
     puzzleId  String
     solved    Boolean
     createdAt DateTime @default(now())
     @@index([userId, createdAt])
     @@index([userId, puzzleId])
   }
   model ChessProfile {
     userId       String   @id            // Student.id или Teacher.id
     puzzleRating Int      @default(1200)
     solved       Int      @default(0)
     failed       Int      @default(0)
     updatedAt    DateTime @updatedAt
   }
   ```
   Миграция руками: `prisma db execute` + `migrate resolve --applied` (локальная БД разошлась с миграциями — см. CLAUDE.md). В той же миграции — `INSERT … ON CONFLICT DO NOTHING` категории `chess` (`levelNumber` 1, без родителя) и её переводов ru/en/hi/zh: тогда предмет появляется и на проде через `migrate deploy`.
7. **Дебюты и тактики — статика в коде**, не в БД: `openings.ts` (≈20 записей: ECO, ключ i18n, главная линия SAN, сторона) из открытого набора `lichess-org/chess-openings` (CC0), курированные руками; `tactics.ts` (≈15: id = тема Lichess, ключ i18n, пример). Прогресс тактики = число решённых задач этой темы (из `ChessPuzzleAttempt` × `themes`). Прогресс дебюта — `localStorage` (просмотрено/доиграно) — ASSUMPTION, сервера хватит позже.
8. **Доска — свой компонент на `chess.js`** (уже стоит), без новой UI-библиотеки: клик-клик и drag (Pointer Events), стрелки и подсветки слоем SVG, координаты, анимация хода CSS-transform. Почему: скины требуют полного контроля над отрисовкой фигур, а текущая страница уже на `chess.js`.
9. **Скины** — реестр `{id, labelKey, light, dark, coords, pieces: Record<'wK'…'bP', () => JSX>}`; фигуры — inline-SVG компоненты (12 на скин). Классика — чистые стаунтон-силуэты. Исключение из правила «только lucide-react»: это иллюстрации, а не иконки интерфейса.
10. **Доска в звонке** — новый режим главного слота `mode: 'chess'` рядом с `'whiteboard'`, сообщения по тому же data channel: `call_chess_start`, `call_chess_state {fen, lastMove, moveAllowed: 'all'|'owner', seq}`, `call_chess_move {from,to,promotion, seq}` (не-владелец шлёт ход; владелец валидирует и рассылает state — владелец единственный источник истины), `call_chess_stop`. Новый участник получает state тем же путём, что и доску-рисовалку. Видимость кнопки: комната знает свой предмет — API комнаты отдаёт `subjectSlug` (по `categoryId`), кнопка при `subjectSlug === 'chess'`.
11. **Курсы** — два новых `TaskBlockType`: `CHESS_PUZZLE {fen, solution: string[] (UCI), sideToMove, prompt?}` и `CHESS_STUDY {fen, moves: {uci, comment?}[]}` — в реестре блоков теста. Курс получает их через уже существующий узел «активный тест»; тест в звонке — тоже. Оценка `CHESS_PUZZLE`: всё или ничего, баллы как у прочих блоков; `CHESS_STUDY` — инфо-блок без баллов.
12. **Маршруты**: `/chess` (хаб), `/chess/play`, `/chess/puzzles`, `/chess/learn` (вкладки «Тактики» / «Дебюты»), `/chess/learn/opening/[id]`. `/game/chess` → редирект на `/chess/play`. Плитка «Курсы» → каталог курсов с фильтром категории `chess`.
13. **Прототипы Hero** — `ForNewDesign/prototypes/chess-hero-{a,b,c}-*.html`, инлайн-свитчер (как у `wallet-*`), три мира: (a) «Партия идёт» — живая доска, где движок играет сам с собой и тренер комментирует; (b) «Галерея скинов» — фигуры-персонажи крупно, бордо/крем позитив-негатив; (c) «Объяснение» — разбор одного зевка: стрелка, оценка, фраза тренера. Без внешних JS, Google Fonts с fallback.

## Дополнение 2026-10-19 (вечер): разбор партии (G19, G20, T16)

После партии (с ботом, онлайн, а также вставкой PGN) — кнопка «Оценить партию» → `/chess/analysis` (данные передаются в `sessionStorage['gw-chess-analysis']` = `{pgn | moves[], initialFen, white, black, result, source}`; для онлайна — `?game=<id>`). Движок в браузере прогоняет все позиции (MultiPV 2, ~0.6 с/позицию, прогресс-бар, отменяется при уходе), затем чистая модель `reviewModel.ts` классифицирует каждый ход по потере вероятности выигрыша (win% = 50 + 50·(2/(1+e^(−0.00368208·cp))−1), с точки зрения сходившего):
- **книжный** — ход совпадает с главной линией одного из `OPENINGS` (префикс партии) в первых 20 полуходах;
- **лучший** — совпал с топ-1 движка;
- **блестящий (алмаз)** — лучший или потеря ≤ 2%, И это жертва (ходящая сторона отдаёт материал ≥ 2 пешки по SEE/«фигура под боем и не защищена»), И позиция после хода не хуже чем −2% от лучшей, И до хода сторона не выигрывала подавляюще (win% < 90);
- **отличный «!»** — лучший, и второй по силе ход хуже на ≥ 15% win% (единственный ход), либо ход переводит проигранную позицию (win% < 30) в равную/лучше;
- **превосходный** — потеря ≤ 2%; **хороший** ≤ 5%; **неточность** ≤ 10%; **ошибка** ≤ 20%; **зевок** > 20%;
- **упущение** — соперник предыдущим ходом ошибся/зевнул, у сходившего был ход с выигрышем ≥ 20% win%, а сыгранный упустил ≥ 10% (и это не зевок).
Точность стороны = 103.1668·e^(−0.04354·средняя потеря win%) − 3.1669, обрезать в 0..100. Счётчик классов по сторонам (как карточка chess.com), график оценки (SVG, клик по точке → ход), листание ходов (стрелки, клавиатура), на доске — значок класса в углу клетки, куда пошли (свои SVG-иконки, цвета классов), стрелка лучшего хода, если сыгранный не лучший; тренер (аватар, `CoachSays`) по кнопке объясняет выбранный ход через `/api/chess/coach` (context 'game', реальные данные разбора). Ключевые моменты — фильтр «показать только ошибки/зевки/блестящие». Живой тренер в партии (5 классов) не меняется.

### Поправки по ревью 16 (решения)
- **D04:** «до хода не выигрывал подавляюще (win% < 90)» для блестящего считается по лучшей альтернативе сыгранному ходу (иначе матующая жертва никогда не блестящая — топ-линия уже ~100%).
- **D05:** вторая ветка «отличного» (спасение проигранной позиции) опирается на win% ДО предыдущего хода соперника: если соперник ошибся/зевнул и сыгранный ход единственный, кто это реализует — это «отличный» через первую ветку; отдельная ветка «< 30 → ≥ 45» убрана как недостижимая без шума движка.
- **D06:** 13.Лxd7 в «Оперной партии» — позиционная жертва (материал после размена равен), по правилу «≥ 2 пешки» не блестящий; ожидание тикета снято. 16.Фb8+ — блестящий.
