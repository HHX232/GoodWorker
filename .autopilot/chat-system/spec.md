# Спецификация: Чат репетитор-ученик

## Задача

Репетитор и ученик сейчас не могут написать друг другу внутри платформы —
только созвониться или разобраться через уведомления, которые не держат
переписку. Репетитору, чтобы напомнить об оплате, назначить домашнее задание
или предложить услугу, приходится делать это «в воздух»: уведомление
приходит, а обсудить детали или прикрепить файл негде.

## Решение

У репетитора и ученика появляется общий чат 1:1 — из профиля репетитора
(карточка ученика и её модалка) и из шапки сайта у обоих. В чате видно,
сколько непрочитанных сообщений, можно писать текст, слать фото/файлы и
голосовые. Когда репетитор назначает домашку, предлагает персональную услугу
или подходит срок напоминания об оплате — в переписке сама появляется
красивая карточка-превью этого события, а не просто текст.

## Решения по реализации

**Модель данных.** Две новые модели, 1:1 через уже существующий `TeacherStudent`:

```prisma
model Conversation {
  id            String   @id @default(uuid())
  teacherId     String
  studentId     String
  createdAt     DateTime @default(now())
  lastMessageAt DateTime @default(now())
  teacher       Teacher  @relation(fields: [teacherId], references: [id], onDelete: Cascade)
  student       Student  @relation(fields: [studentId], references: [id], onDelete: Cascade)
  messages      ChatMessage[]

  @@unique([teacherId, studentId])
  @@index([teacherId, lastMessageAt])
  @@index([studentId, lastMessageAt])
}

model ChatMessage {
  id             String       @id @default(uuid())
  conversationId String
  senderRole     Role
  text           String?
  attachmentUrl  String?
  attachmentType String?   // "image" | "file" | "audio"
  attachmentName String?
  attachmentSize Int?
  eventType      String?   // "HOMEWORK_ASSIGNED" | "PERSONAL_SERVICE" | "PAYMENT_REMINDER" — null для обычных сообщений
  eventPayload   Json?
  isRead         Boolean      @default(false)
  createdAt      DateTime     @default(now())
  conversation   Conversation @relation(fields: [conversationId], references: [id], onDelete: Cascade)

  @@index([conversationId, createdAt])
}
```

Почему так: диалог создаётся лениво (get-or-create) при первом открытии чата с
человеком, а не отдельным действием «начать чат» — раз `TeacherStudent` уже
связывает их, отдельный шаг создания диалога был бы лишним экраном (R01.1).
`senderRole` вместо двух nullable-полей (`teacherId`/`studentId` отправителя)
— отправитель уже известен из роли + `conversationId` однозначно даёт вторую
сторону. `eventType`/`eventPayload` на самом сообщении, а не отдельной
таблицей — карточка события это сообщение с доп. разметкой, а не другая сущность
(проще рендерить единым списком, сортировка по времени работает бесплатно).

**API** (`app/api/chat/`):
- `GET /conversations` — список диалогов текущего пользователя (для TEACHER — по всем его `TeacherStudent`, для STUDENT — по всем его репетиторам), с другой стороной, превью последнего сообщения, `unreadCount` на диалог. Поиск (R06) — на клиенте, сервер параметр не принимает.
- `POST /conversations` — `{otherId}` → get-or-create диалог, проверка что связь `TeacherStudent` существует (иначе 403).
- `GET /conversations/[id]/messages?before=<messageId>&limit=30` — история, курсор назад по времени.
- `POST /conversations/[id]/messages` — `{text?, attachmentUrl?, attachmentType?, attachmentName?, attachmentSize?}`, хотя бы одно из text/attachment.
- `PATCH /conversations/[id]/read` — отметить прочитанным всё от собеседника.
- `GET /unread-count` — суммарное число непрочитанных по всем диалогам (для бейджа у колокольчика, R04.1).

Загрузка файлов — существующий `POST /api/upload` (S3, уже есть авторизация,
50 МБ серверный потолок, denylist опасных расширений) с `folder=chat`;
чат добавляет свой клиентский лимит 10 МБ поверх (R16) и серверную проверку
`attachmentSize` при записи сообщения — не переизобретаю аплоадер.

**Сжатие изображений** (R11.2) — новый клиентский хелпер рядом с уже
существующим `compressImageToBase64` (тот отдаёт data URL для превью,
для аплоада нужен `File`): `canvas.toBlob('image/jpeg', 0.75)` с тем же
ресайзом до разумного максимума перед отправкой в `uploadFile`.

**Реалтайм** (R19i) — поллинг, не WebSocket/SSE: список диалогов и бейдж
у колокольчика — раз в 15 секунд (как `NotificationBell` уже поллит
уведомления раз в 60 секунд — паттерн в проекте есть, беру его же, только
чаще, чат subjectively более «живой»); открытый диалог — раз в 3 секунды,
только пока вкладка на экране (`document.visibilityState`), останавливается
при уходе со страницы.

**Карточки событий** (R13–R15):
- Домашнее задание и персональная услуга — сообщение с `eventType` создаётся
  той же серверной операцией, что уже создаёт `Notification` (`app/api/homework/route.ts`
  после `createNotification({type: HOMEWORK_ASSIGNED, …})`; аналогично для
  персональной услуги в `app/api/services/route.ts`) — тот же payload
  (`homeworkId`/`assignmentId` и т.п.), чтобы карточка в чате и уведомление
  показывали одно и то же.
- Напоминание об оплате — тот самый checkpoint-механизм из `tg-bot/src/scheduler.ts`
  (`sendPaymentReminders`), который уже один раз на превышение порога шлёт
  Telegram и создаёт `Notification`; туда же добавляется третий побочный
  эффект — вставка `ChatMessage` с `eventType: "PAYMENT_REMINDER"` в диалог
  (get-or-create по teacherId/studentId, той же raw-SQL техникой, что уже
  используется для `Notification`). Один и тот же момент решает, когда
  сработать, — не завожу параллельный триггер.

**Доступ.** Каждый эндпоинт проверяет: диалог принадлежит текущему
пользователю (`teacherId`/`studentId` совпадает с сессией), а при
get-or-create — что связь `TeacherStudent(teacherId, studentId)` существует.
Без неё чат создать нельзя ни с одной стороны.

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| `chat/data` (API-роуты `app/api/chat/*`) | таблицы `Conversation`/`ChatMessage`, права доступа | HTTP-контракт выше (conversations/messages/read/unread-count) | get-or-create диалога, подсчёт unread, проверку `TeacherStudent` |
| `ChatWidget` (страница `/chats` + список + диалог + композер) | весь UI чата, поллинг, локальное состояние отправки | `<ChatWidget initialStudentId?/>`; используется страницей `/chats` | вёрстку пузырей/карточек событий, логику intervals |
| `ChatEntryPoints` (кнопка в `StudentDetailModal`, бейдж в `DashboardStudentSidebar`, иконка в `Header`, кнопка в `DashboardCenter`) | только точки входа, никакой чат-логики | ссылки на `/chats?studentId=…` / `/chats` | ничего не прячет — это тонкие обвязки существующих компонентов |
| `event-cards` (общая функция вставки `ChatMessage` с `eventType`, дергается из `homework`, `services`, tg-bot cron) | формирование `eventPayload` по типу события | `postEventCard({teacherId, studentId, eventType, payload})` | get-or-create диалога изнутри — вызывающий код передаёт только пару id |

Швы для тестов — реальные HTTP-вызовы через `app/api/chat/*` с реальной
сессией (как уже делалось в этой сессии для календаря и платежей), а не unit
на изолированных функциях: в проекте нет тестового раннера (см. `CLAUDE.md`
прототипов — тут то же самое верно для основного приложения), проверка —
curl-сценарии поверх поднятого dev-сервера.

## Вне рамок

| Требование | Почему не сейчас |
|---|---|
| R19i — WebSocket/SSE вместо поллинга | в деплое (Vercel/Railway serverless-функции для API) нет готовой инфраструктуры двусторонних соединений; поллинг закрывает «реалтайм» ощутимо дешевле и без нового сервиса |
| Групповые чаты, чаты вне пары «мой репетитор/мой ученик» | бриф говорит только про пару репетитор-ученик; групповые обсуждения — отдельная задача |
| Пересылка/реакции/редактирование сообщений | не упомянуто в брифе — базовый чат сначала должен просто работать |
| Реальное сжатие видео/аудио перед загрузкой | R16 просит сжатие «для начала» — беру только сжатие изображений (самый частый и самый тяжёлый по объёму случай), аудио с ГС и так короткое (голосовые), видео не входило в перечисленные типы вложений |
| Пуш-уведомления браузера о новом сообщении | не в брифе; бейджи в шапке и на карточке ученика уже покрывают «вижу, что есть новое» без выхода за рамки задачи |

## Открытые места
