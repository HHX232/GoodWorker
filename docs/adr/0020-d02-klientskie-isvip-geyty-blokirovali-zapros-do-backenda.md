# 0020. D02 — клиентские isVip-гейты блокировали AI-запрос до бэкенда

## Контекст

Тикеты 02–03 явно фиксировали: «клиентский код не требует правок» — бэкенд снял
`isVip`-проверку (ADR 0018 / G01), фронтенд якобы только обрабатывает ответ сервера.

## Решение

Ревью тикета 06 показало обратное: на фронтенде остались независимые клиентские гейты —
`CalendarCreateModal.handleGeneratePlan` блокировал вызов при `!isVip` ещё до `fetch` к
`lesson-plan`, `canUseAi = isVip || isAdmin` в `FormulaKeyboard` блокировал открытие
AI-панели до вызова `formula-ai`/`formula-photo`. В обоих случаях запрос физически не
уходил на сервер — не-VIP пользователь с деньгами на балансе не мог воспользоваться
фичей вообще (недостижима была даже 402-модалка из R17). Оба гейта сняты в рамках
тикета 06.

## Почему

Изначальное допущение «фронтенд только обрабатывает ответ бэкенда» рассматривало клиент
как пассивный слой — отвергнуто по факту: клиент содержал собственную, независимую от
бэкенда бизнес-логику доступа (UI сам решал, показывать ли форму, ещё до похода на
сервер), которую предположение тикетов 02/03 не учло. Альтернативы не было —
недостижимый UI для целевой аудитории G01 (не-VIP с балансом) прямо противоречил цели
брифа, оставлять как есть означало не выполнить R17.

## Последствия

«Бэкенд как источник правды» на этом проекте не гарантирует, что фича доступна с
фронтенда — доступность приходится сверять в обоих слоях отдельно при каждом подобном
гейт-изменении. Ложное допущение тикетов 02/03 попало в манифест как «done» и вскрылось
только на ревью тикета 06 — будущие похожие рефакторинги доступа должны явно `grep`-ать
клиентские `isVip`/`isAdmin` проверки, а не только серверные 403/402.
