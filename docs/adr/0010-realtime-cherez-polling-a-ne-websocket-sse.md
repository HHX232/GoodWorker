# 0010. Реалтайм чата через поллинг, а не WebSocket/SSE

**Контекст**
Деплой — serverless-функции (Vercel/Railway-подобная модель) без готовой инфраструктуры долгоживущих соединений. В проекте уже есть прецедент: `NotificationBell` поллит уведомления раз в 60 секунд.

**Решение**
Список диалогов и бейдж непрочитанных обновляются поллингом раз в 15 секунд; открытый диалог — раз в 3 секунды, только пока вкладка видима (`document.visibilityState`), останавливается при уходе со страницы. WebSocket/SSE не используются.

**Почему**
Рассмотрели WebSocket/SSE — отвергли: текущий serverless-деплой не держит долгоживущее соединение из коробки, для этого нужен либо отдельный сервис/провайдер (Pusher, Ably, свой сокет-сервер), либо смена модели хостинга API — несоразмерная инфраструктурная инвестиция ради ощущения «живости», которое интервал в 3 секунды закрывает практически неотличимо для пользователя чата 1:1 с низким трафиком.

Взяли уже проверенный в проекте паттерн (`NotificationBell`), только с более частым интервалом для более «живого» ощущения — не вносили в кодовую базу новый примитив синхронизации ради одной фичи.

**Последствия**
Задержка на новое сообщение — до 3 секунд в открытом диалоге, до 15 секунд — на бейдж и список в худшем случае. Нагрузка на сервер растёт линейно с числом одновременно открытых вкладок/диалогов — при росте пользователей это упрётся в лимиты раньше, чем при push-модели. Переход на WebSocket/SSE в будущем — не инкрементальный апгрейд поверх текущего кода, а отдельная инфраструктурная задача: новый сервис или провайдер плюс переработка клиентского состояния вокруг событий вместо интервалов.
