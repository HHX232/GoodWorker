# 0012. Вложения чата через существующий /api/upload, сжатие только для изображений

**Контекст**
В проекте уже есть `POST /api/upload` (S3, авторизация, серверный потолок 50 МБ, denylist опасных расширений). Чату нужен свой лимит 10 МБ и сжатие хотя бы для самого частого и тяжёлого случая — фото с телефона.

**Решение**
Чат грузит вложения через существующий `POST /api/upload` с `folder=chat`, добавляя поверх свою клиентскую проверку 10 МБ и серверную проверку `attachmentSize` при записи сообщения. Перед отправкой сжимаются (canvas → JPEG, качество 0.75) только изображения; документы и голосовые в этой итерации уходят как есть, но под тем же лимитом 10 МБ.

**Почему**
Рассмотрели отдельный аплоадер для чата (свой путь/эндпоинт с изначально урезанным потолком) — отвергли: существующий `/api/upload` уже решает авторизацию и denylist опасных расширений, второй аплоадер стал бы вторым местом, которое нужно чинить при любой будущей правке безопасности загрузок — риск расхождения политик между двумя точками входа в S3.

Рассмотрели сжатие всех типов вложений (видео/аудио/документы) сразу — отвергли для первой итерации: видео не входит в перечисленные бриф-типы вложений, голосовые и так короткие по своей природе, а сжатие произвольных документов на клиенте — отдельная задача, не связанная с исходным кейсом «первая же фотография с телефона расходует весь лимит».

**Последствия**
Документы и голосовые расходуют лимит 10 МБ без права на пересжатие — пользователь с тяжёлым файлом получит отказ там, где для фото решение бы сжало и пропустило. Полное сжатие всех типов вложений явно осталось вне рамок и потребует отдельного захода — клиентского кодека/библиотеки для аудио/видео, которых в проекте сейчас нет. Лимит и логика сжатия завязаны на контракт `/api/upload` — если он изменит потолок или формат ответа, чат меняется вслед за ним, а не независимо.
