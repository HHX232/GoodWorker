# 0017. Каждому участнику звонка достаётся своя копия конспекта

**Контекст**
Мастер-конспект принадлежит владельцу комнаты. Ученики и репетитор должны получить его в своё хранилище, причём ученики — в «Мои файлы» (`StudentFile`), репетитор — в библиотеку (`TutorFile`); оба типа файлов связываются с конспектом через `lectureNoteId`. До этого `VideoCallParticipant.userId` не заполнялся.

**Решение**
В финале урока для каждого участника (владелец плюс все уникальные `VideoCallParticipant.userId`) создаётся собственная `LectureNote` с копией документа. У владельца копией служит сам мастер. К каждой копии прикладывается свой .docx, свой файл в хранилище и своё уведомление. Чтобы знать участников, выдача токена `POST /api/livekit/token` делает `upsert` `VideoCallParticipant` с `userId` и `userRole`. Не-VIP участники тоже получают файл и могут его править.

**Почему**
Отвергли один общий `LectureNote` со ссылкой для всех: у файла в хранилище должен быть владелец, квота и папка именно этого человека; правка одним участником молча меняла бы чужой конспект; отзыв доступа или удаление у одного ломали бы остальных. Отвергли и вариант «положить файл только владельцу», потому что бриф требует хранилище для всех участников.

`userId` берётся при выдаче токена, а не с клиента: клиент шлёт лишь `identity`, а доверять ему авторство нельзя.

**Последствия**
N участников дают N копий одного текста: хранилище растёт, а после урока копии расходятся независимо и не синхронизируются. Если у участника кончилось место, копия `LectureNote` всё равно создаётся, а уведомление ведёт в `/lecture/<id>`, не в папку. Участник, не получивший токен через наш эндпоинт (или комната не в БД), конспекта не получит. Финал обязан быть идемпотентным (захват `RECORDING→FINALIZING`, уникальность по `(callRoomId, ownerId, ownerRole)`), иначе повторное завершение плодит дубли.
