# 0013. D01 — владение чтением ?conversationId= закреплено за модулем диалога, не за точками входа

**Контекст (что план предполагал)**
План разбил работу по зонам владения: T02 сознательно исключил из своей зоны чтение query-параметра диалога на странице `/chats`, а T06 (точки входа — кнопка в `StudentDetailModal` и т.п.) не имел права трогать `ChatShell`/`app/chats/page.tsx` — не его зона. При этом ни один тикет не был явно назначен ответственным за то, чтобы «Перейти в чат» из карточки ученика открывало именно этот диалог, а не просто список чатов — граница ответственности за query-параметр выпала между двумя тикетами.

**Решение (что код доказал)**
Функциональность довершена дозапросом внутри T03 — тикета, владеющего `ChatShell`/диалогом: добавлен `ChatShell.initialConversationId`, а `ChatPage` читает `?conversationId=` из URL и передаёт значение дальше. Чтение параметра, управляющего состоянием чата, закреплено за тем же модулем, что владеет самим диалогом, а не за точками входа, которые лишь передают ID в URL.

**Почему**
Разбиение по зонам владения (data/widget/entry-points) само по себе оправдано, но декомпозиция не покрыла стык между точкой входа (кладёт ID в URL) и виджетом (должен прочитать ID и открыть нужный диалог) — ни один тикет по границам из спецификации формально не отвечал за этот шов. Закрепление чтения `conversationId` за `ChatShell`/`ChatPage` логично: только модуль, которому принадлежит диалог, знает, как именно открыть конкретный диалог из списка.

**Последствия**
Любой новый query-параметр, управляющий состоянием `ChatShell` (поиск, фильтр, второй открытый диалог и т.п.), по умолчанию должен закрепляться за `ChatShell`/`ChatPage`, а не за модулем, который на чат просто ссылается. Эта граница решена прецедентно ревью, но не отражена в исходной таблице «Границы и швы» спецификации чата — следующая декомпозиция тикетов должна внести её туда явно, а не полагаться на память об этом разборе.
